# Задание 2. Выбор и настройка мониторинга в системе

Технический документ: что и как измеряем в системе «Александрит» и зачем это бизнесу.

---

## 1. Мотивация

Сейчас единственный источник данных — Яндекс.Метрика, и она покрывает только веб-фронт онлайн-магазина (B2C). Заказы через публичный API идут в обход браузера (партнёры → API → MES → очередь → CRM), и Метрика их не видит. Бэкенд, очереди и API не покрыты мониторингом — а именно там, по симптомам, теряются и застревают заказы.

Что даёт мониторинг бизнесу:

- **Обнаружение проблем до жалобы клиента.** Сейчас о сбоях узнают из обращений; мониторинг с алертингом позволяет реагировать раньше.
- **Отправная точка для улучшений.** Метрики дают baseline, по которому видно эффект каждой инициативы (например, сократился ли backlog расчёта).
- **Проверка гипотез.** Гипотезу «узкое место — очередь расчёта, а не производство» подтверждают метрики глубины очереди и времени расчёта. Это экономит бюджет на неправильное масштабирование.
- **Защита выручки.** Бизнес-метрики (воронка по статусам, доля зависших заказов, возраст самого старого необработанного заказа) позволяют увидеть проблему до потери контракта.
- **Прозрачность SLA для B2B-партнёров.** Метрики времени прохождения заказа позволяют держать и подтверждать SLA.

Ожидаемый эффект: снижение MTTD/MTTR (время обнаружения/восстановления), рост доли заказов, прошедших полный цикл в срок, снижение доли зависших заказов и нагрузки на поддержку.

---

## 2. Выбор подхода к мониторингу

Для разных частей системы применяем разные подходы — так рекомендуется, потому что природа компонентов разная (запрос-ответные сервисы vs ресурсы vs очереди).

| Часть системы | Подход | Почему |
|---------------|--------|--------|
| Онлайн-магазин (BE), CRM (BE), публичный API, MES-бэкенд (запрос-ответные сервисы) | **RED** (Rate, Errors, Duration) | Это сервисы, обрабатывающие запросы. RED прямо отвечает на вопрос «сколько запросов, сколько ошибок, как быстро» — то, что важно для пользователей и партнёров. |
| Инфраструктура: EC2-инстансы, БД, RabbitMQ-брокер как ресурс, диски (ресурсы) | **USE** (Utilization, Saturation, Errors) | Это ресурсы. USE отвечает «насколько загружен, есть ли очередь ожидания, есть ли ошибки ресурса» — идеально для CPU/RAM/диска/пулов соединений. |
| Сквозной пользовательский путь заказа + сервисы целиком (верхнеуровнево) | **Четыре золотых сигнала** (Latency, Traffic, Errors, Saturation) | Обобщающий взгляд «сверху» на здоровье сервиса, включает Saturation — критично для нашего случая (очереди, single-instance). Используем как «зонтик» над RED, добавляя Saturation. |

**Практически:** RED — для эндпоинтов и консюмеров, USE — для железа/БД/брокера, Golden Signals — для дашбордов верхнего уровня и SLO-алертов.

## 3. Метрики: что, где и зачем

Соглашения к таблице:
- Обозначения типа: **[R]** — RED, **[U]** — USE, **[G]** — Golden Signals, **[B]** — бизнес.
- Все метрики дополнительно несут ярлык `env` (dev/release/prod) — в таблице не дублируем.

| Группа | Метрика | Тип | Зачем | Ярлыки |
|--------|---------|-----|-------|--------|
| Сервисы | Requests / RPS (shop, CRM, MES API), в т.ч. per user | [R][G] | Реальная нагрузка и её рост (+100/мес, всплеск от API); срез per user (ярлык `user_id`) выявляет злоупотребление API конкретным партнёром. | `service`, `endpoint`, `user_id` |
| Сервисы | HTTP-ответы по статусам (HTTP 200 / HTTP 500 для shop, CRM, MES) | [R][G] | Один счётчик `requests_total` с ярлыком `status_code` заменяет отдельные счётчики 200/500; доля 500 — прямой индикатор ошибок (error rate). | `service`, `endpoint`, `status_code` |
| Сервисы | Response time / latency (shop, CRM, MES API), p50/p95/p99 | [R][G] | Скорость ответа; деградация p95/p99 — ранний признак насыщения; для API — часть SLA. | `service`, `endpoint` |
| Сервисы | Number of simultaneous sessions (shop, CRM, MES) | [G][U] | Число одновременных сессий — уровень параллельной нагрузки и насыщение обработчиков (важно при одном инстансе). | `service` |
| Сервисы | KB received / sent (shop, CRM, MES) | [U] | Объём сетевого трафика вход/исход; аномалии и узкие места. | `service`, `direction` |
| Инфраструктура | CPU % (shop, CRM, MES) | [U] | Загрузка CPU инстансов; предвестник деградации на одном инстансе. | `service`, `instance` |
| Инфраструктура | Memory Utilisation (shop, CRM, MES API + shop db, MES db) | [U] | Память сервисов и инстансов БД; риск OOM/свопа. | `service`, `db`, `instance` |
| Инфраструктура | Number of connections (shop db, MES db) | [U] | Число соединений к БД; исчерпание пула = отказы (тяжёлый дашборд MES «съедает» соединения). | `db` |
| Инфраструктура | Size of shop db / MES db instance | [U] | Рост объёма БД; планирование ёмкости; напрямую влияет на скорость дашборда MES. | `db` |
| Инфраструктура | Size of S3 storage | [U] | Рост файлового хранилища (3D-модели, чеки, экспорты); планирование ёмкости и затрат. | `bucket` |
| Очереди/расчёт | Number of dead-letter-exchange letters (RabbitMQ) | [U][B] | Недоставленные сообщения = потерянные заказы; прямой индикатор проблемы «заказ не дошёл». | `queue` |
| Очереди/расчёт | Number of messages in flight (RabbitMQ) | [U] | Сообщения в обработке (unacked); зависшие = подвисший/упавший консюмер. | `queue` |
| Очереди/расчёт | Queue depth — глубина очереди (backlog) | [U][G] | Ключевая метрика: backlog расчёта копится → заказы застревают. Проверяет гипотезу об узком месте перед производством. | `queue` |
| Очереди/расчёт | Message age — возраст старейшего сообщения | [U][B] | Сколько заказ реально ждёт обработки; прямая связь с жалобами на долгие сроки. | `queue` |
| Очереди/расчёт | Price calculation duration (2–30 мин) | [R][B] | Распределение времени расчёта; планирование числа воркеров и приоритетов. | `complexity_bucket` |
| Очереди/расчёт | Consumer throughput — обработано/сек | [R] | Пропускная способность воркеров; сравнение с input rate показывает, справляемся ли. | `queue`, `consumer` |
| Бизнес | Заказы по статусам (воронка INITIATED…CLOSED) | [B] | На каком этапе застревают заказы. | `status`, `channel`, `partner_id` |
| Бизнес | Время перехода между статусами (`SUBMITTED → PRICE_CALCULATED` и др.) | [B] | Замер времени жизни заказа против обещанных 3 недель. | `from_status`, `to_status`, `channel` |
| Бизнес | Возраст старейшего заказа «в работе» / доля зависших | [B] | Ранний сигнал о зависании до жалобы клиента; KPI здоровья потока заказов. | `status`, `channel`, `partner_id` |
| Бизнес | Доля заказов, дошедших до CLOSED в срок | [B] | Итоговый бизнес-результат. | `channel`, `partner_id` |

Осознанно **не заводим отдельные метрики** там, где их заменяет ярлык: отдельные «HTTP 200» и «HTTP 500» на каждый сервис — это один счётчик `requests_total` с ярлыками `service` и `status_code`; отдельные «RPS per user» — тот же счётчик с ярлыком `user_id`. Это устраняет дублирование и «взрыв» числа метрик.

## 4. План действий (драфт ТЗ)

Высокоуровневые задачи для реализации:

1. **Развернуть хранилище метрик** (time-series БД, например Prometheus или VictoriaMetrics) — сюда будут стекаться все метрики.
2. **Развернуть Grafana** и собрать дашборды: обзор, сервисы, инфраструктура, очереди/расчёт, бизнес-воронка заказов.
3. **Добавить сбор метрик в приложения** (магазин, CRM, MES, API) — чтобы каждый сервис отдавал свои RPS, ошибки, latency и т.д.
4. **Собрать метрики RabbitMQ** — глубину очередей, DLQ, сообщения в обработке.
5. **Собрать метрики инфраструктуры** — CPU, память, диск EC2-инстансов и размеры/соединения managed-БД в Yandex Cloud.
6. **Добавить бизнес-метрики** — при смене статуса заказа отправлять событие в мониторинг; возраст и долю зависших заказов считать по БД по расписанию.
7. **Настроить алертинг** — правила по техническим порогам (ошибки, latency, насыщение) и по бизнес-SLA (глубина очереди, возраст заказа, DLQ); оповещения в мессенджер и on-call.
8. **Определить целевые значения (SLO)** — например, «95% заказов проходят `SUBMITTED → PRICE_CALCULATED` менее чем за 1 ч», «доступность API 99.9%».
9. **Задокументировать** метрики и инструкции по реакции на алерты.

Порядок запуска: сначала метрики инфраструктуры и очередей (быстро внедряются и сразу проверяют главную гипотезу об узком месте), затем метрики сервисов, затем бизнес-воронка.

## 5. Дополнительно: показатели насыщенности (saturation) и реакция

Насыщение — самый релевантный для «Александрита» сигнал (один инстанс, одна БД, длинный расчёт). Пороги и реакция:

| Ресурс/показатель | Порог насыщения | Почему такой | Что происходит при превышении |
|-------------------|-----------------|--------------|-------------------------------|
| CPU инстанса | > 80% в течение 5 мин | Запас на всплески; выше 80% ответы начинают тормозить. | Предупреждение и заявка на добавление мощности; при критической загрузке (> 95%) — срочно будим дежурного. |
| Memory | > 85% | Риск нехватки памяти и падения сервиса. | Оповещение и заявка; проверяем утечку памяти, при необходимости увеличиваем инстанс. |
| Disk | > 80% | Заканчивается место (особенно под логи и БД). | Оповещение; автоматически чистим старые данные или расширяем диск. |
| DB connections | > 85% от лимита | Если соединения закончатся — сервис начнёт отказывать. | Оповещение; разбираемся, кто занимает соединения (например, дашборд), увеличиваем лимит; в перспективе выносим тяжёлые чтения на реплику. |
| **Queue depth (очередь расчёта)** | > 500 сообщений **или** растёт без остановки 15 мин | Заказы приходят быстрее, чем обрабатываются — прямая причина зависаний. | Автоматически добавляем воркеров расчёта в MES и шлём оповещение; если очередь не уменьшается — будим дежурного. |
| **Message age (старейшее сообщение в очереди)** | > 30 мин (верхняя граница нормального расчёта) | Дольше — это уже сбой, а не просто сложная модель. | Срочное оповещение дежурному и заявка; проверяем, не завис ли обработчик. |
| **DLQ size (недоставленные сообщения)** | > 0 (хотя бы одно сообщение) | Сюда попадают заказы, которые не дошли, — это потерянная выручка. | Немедленное оповещение и заявка на ручной разбор; повторная попытка доставки по правилам. |
| Latency p99 API | > 2× от обычного, 10 мин | Задержки, которые почувствуют партнёры. | Оповещение; при необходимости временно ограничиваем поток запросов. |
| Возраст заказа «в работе» | > 3 недель (обещанный срок), предупреждение за неделю до | Прямое нарушение обещания клиенту. | Оповещение продакту и поддержке, разбор по конкретному заказу, чтобы связаться с клиентом заранее. |

**Общая логика реакции (по нарастанию):**
1. **Автоматически, без участия человека** — там, где это безопасно: добавить воркеров при росте очереди, почистить/расширить диск, повторить доставку недоставленных сообщений.
2. **Завести заявку (не срочно)** — когда ресурс подходит к пределу, но угрозы прямо сейчас нет (CPU / память / диск в «жёлтой» зоне).
3. **Срочно разбудить дежурного** (звонок или пуш) — на критичные ситуации: появились недоставленные сообщения, заказ ждёт слишком долго, очередь лавинообразно растёт, API недоступен.
4. **Сообщить продакту и поддержке** — по бизнес-порогам (заказ приближается к обещанному сроку), чтобы связаться с клиентом до того, как он пожалуется.
