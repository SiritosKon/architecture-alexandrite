# Задание 1. Планирование: анализ, идентификация проблем и поиск решений

## 1. Проблемы

Единый список проблемных мест (существующих и потенциальных), выявленных из схемы и описания системы.

| № | Проблема | Последствие для бизнеса |
|---|----------|-------------------------|
| P1 | Нет мониторинга инфраструктуры и бизнес-метрик (Яндекс.Метрика видит только веб-фронт B2C, не видит API/бэкенд/очереди). | Проблемы обнаруживаются только со слов клиентов; нет отправной точки для улучшений. |
| P2 | Нет распределённого трейсинга: заказ проходит 3 системы + очереди, проследить его путь невозможно. | Нельзя понять, где заказ «завис» или «потерялся»; разбор занимает дни. |
| P3 | Нет централизованного логирования: логи разбросаны по инстансам. | Разбор инцидентов «со слов клиента», высокая нагрузка на поддержку и разработку. |
| P4 | Нет алертинга. | О сбое узнают постфактум, когда клиент уже потерян. |
| P5 | Сообщения в RabbitMQ теряются: нет гарантий доставки (DLQ, ретраи, ack, персистентность, идемпотентность). | Заказ не доходит до CRM → партнёр/клиент «не получил заказ»; прямая потеря выручки и контрактов. |
| P6 | Нет transactional outbox: изменение статуса в БД и публикация события не атомарны. | Рассинхрон между БД и очередью: статус изменился, а событие не ушло (или наоборот). |
| P7 | Нет мониторинга очередей (глубина, возраст сообщений, скорость обработки). | Backlog копится незаметно до жалоб. |
| P8 | Расчёт стоимости долгий (2–30 мин) и обрабатывается, судя по всему, единственным инстансом MES; при росте потока очередь на расчёт копится быстрее, чем разгребается. | Заказы застревают на переходе `SUBMITTED → PRICE_CALCULATED` на недели/месяцы (узкое место ПЕРЕД производством). |
| P9 | Публичный API, вероятно, использует расчёт синхронно (запрос-ответ), хотя операция длится минуты. | Таймауты, повторные запросы партнёров, дубли, ещё большая нагрузка. |
| P10 | Нет приоритизации очереди расчёта. | Нельзя «протолкнуть» важные/крупные заказы. |
| P11 | Каждое приложение — 1 инстанс; нет балансировщика и автоскейлинга. | Единая точка отказа (SPOF), деградация под растущей нагрузкой. |
| P12 | БД — 1 инстанс на чтение и запись, без реплик и failover. | Тяжёлые чтения конкурируют с записями; при отказе — простой; риск потери данных. |
| P13 | Нет rate limiting / backpressure / квот на публичном API. | «Завалило заказами»: неконтролируемый вход перегружает всю цепочку. |
| P14 | Первая страница MES (дашборд «заказы в работе») грузится медленно даже после фильтра и пагинации (нет индексов под сортировку «новые сверху», запрос по всей растущей истории заказов — активные вперемешку с закрытыми, конкуренция за БД, нет кеша). | Плохой UX для операторов и замедление рабочих процессов в MES. |
| P15 | Статус заказа меняется в 3 системах, единого источника правды нет. | Возможны рассинхроны, гонки, «непонятное состояние» заказа. |
| P16 | Длинный путь создания B2B-заказа: партнёр → API → MES считает → очередь → CRM создаёт заказ (много точек отказа). | Потеря сообщения на любом шаге = заказ не появляется в CRM (жалобы партнёров). |
| P17 | E2E-тесты прогоняются вручную одним QA; баги high/highest блокируют прод; задержки релизов растут. | Медленная доставка исправлений — а чинить сейчас нужно много и быстро. |
| P18 | Нет автоматизации тестов (только прототипы у QA). | Ручной регресс не масштабируется вместе с ростом системы. |

## 3. Ответы на вопросы задания

### 3.1. Целевая архитектура через полгода

Через полгода «Александрит» должен прийти к следующему состоянию:

- **Наблюдаемость как основа.** Развёрнут стек: time-series БД (Prometheus/VictoriaMetrics) + Grafana + Alertmanager; распределённый трейсинг на OpenTelemetry (коллектор + Jaeger/Tempo) сквозь все три приложения, очереди и публичный API; централизованное структурное логирование (OpenSearch/ELK). Настроен алертинг по золотым сигналам и бизнес-SLA («заказ не сменил статус N часов»).
- **Надёжный событийный обмен.** RabbitMQ с persistent-сообщениями, DLQ, ретраями с backoff, ack и идемпотентностью; публикация через transactional outbox; глубина и возраст очередей под мониторингом.
- **Расчёт стоимости — асинхронный конвейер.** Долгий расчёт вынесен в масштабируемый пул воркеров MES с приоритетной очередью. Публичный API принимает заявку асинхронно (202 Accepted) и уведомляет партнёра webhook’ом по завершении — без блокирующих таймаутов.
- **Масштабирование и отказоустойчивость.** Приложения за балансировщиком, минимум по 2 инстанса, автоскейлинг. БД с read-репликами (тяжёлые чтения дашборда — на реплику) и настроенным failover.
- **Производительность MES.** Дашборд ускорен: кеш (Redis) + корректные индексы + разделение горячих/холодных заказов + чтение с реплики.
- **Защищённый API.** API-gateway с rate limiting и квотами по партнёрам.
- **Процессы.** Автоматизированный E2E-регресс, сокращающий задержки релизов.

Итог: система, в которой команда **видит** состояние заказов и инфраструктуры в реальном времени, заказы **не теряются и не застревают**, а инфраструктура **масштабируется вместе с линейным ростом** нагрузки.

### 3.2. Топ-3 инициативы, если можно сделать только три за полгода

1. **Наблюдаемость: мониторинг + трейсинг (приоритеты 1–2).**
   Сейчас все выводы о причинах — гипотезы, а решения по инфраструктуре дорогие. Мониторинг и трейсинг дают отправную точку и подтверждают, где именно теряются и зависают заказы (очередь, расчёт или путь через API). Дёшево относительно эффекта, разблокирует все остальные решения.

2. **Надёжность обмена + асинхронный масштабируемый расчёт стоимости (приоритеты 4–5).**
   Это прямая причина основных проблем: заказы теряются (потеря сообщений) и застревают месяцами (backlog расчёта на единственном инстансе). Это напрямую стоит компании контрактов и выручки, поэтому идёт сразу после внедрения наблюдаемости.

3. **Кеширование и ускорение дашборда MES (приоритет 6).**
   Быстрая локальная задача: устраняет долгую загрузку дашборда, которым сейчас неудобно пользоваться, и снижает нагрузку на чтение БД. Низкая стоимость, не блокирует остальные инициативы.
